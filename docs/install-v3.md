# Установка и переустановка TaskTracker v3

Установщик вызывается защищённым `Rebuild-TaskTracker.ps1` после административного bootstrap. Исходный код он берёт из чистой локальной ветки `main`, совпадающей с локальной `origin/main` и commit в `bootstrap.json`. Рабочая служба не выполняет файлы из клона.

Родительский каталог Tracker должен принадлежать Administrators/SYSTEM. Обычным пользователям разрешён `Modify`, но не удаление дочерних объектов, изменение ACL или владельца. Корень Tracker не наследует права родителя; его допустимый владелец — Administrators, SYSTEM или фактическая сервисная учётная запись. Сервисная учётная запись получает полный доступ, целевой пользователь — только чтение и проход. Явный `-TrustAuthenticatedUsers` допускает более широкие права родителя при сознательном доверии их получателям.

При установке и переустановке корневой `bootstrap.ps1` берёт корень снимков из `GIT_FOLDER` целевого пользователя; явный `-SnapshotRoots` задаёт один или несколько других абсолютных корней. Внутренний административный bootstrap получает выбранные корни параметром, а установщик записывает их в `service.json`. Пустой список запрещён. Перед остановкой службы скрипт проверяет целевого пользователя, путь Tracker, корни проектов, ACL, фактическую сервисную учётную запись и привязку Windows-службы. Он создаёт временные `bin` и `runtime` внутри `.protected`, через Windows launcher `py.exe` выбирает версию из `.venv/python_version.txt` без fallback, создаёт venv, устанавливает `requirements.txt` через pip, проверяет импорт worker и компилирует C# host только при изменении `src/ServiceHost.cs`. Если исходник host не изменился, установленный EXE копируется побайтно.

После подготовки скрипт создаёт либо сверяет две копии MCP-токена, останавливает работающую службу, переключает установленные `bin`, `runtime` и `service.json`, запускает службу и проверяет состояние `Running/Automatic` и запрос MCP с токеном. При ошибке он возвращает прежние каталоги, конфигурацию, обе копии токена и ACL, удаляет вновь созданные службу и учётную запись и восстанавливает прежнее состояние службы. Если откат не завершился, старые файлы сохраняются в `.protected/.rollback-*`, а ошибка помечается `RECOVERY_INCOMPLETE`.

Установщик не запускает Codex CLI, не запрашивает пароль TargetUser и не меняет его плагины. После установки TargetUser сам проверяет Git marketplace `https://github.com/twilight-slider/ai-marketplace.git` и при необходимости устанавливает из него `task-folder-workflow@ai-marketplace` 0.6.1 и `task-tracker-mcp@ai-marketplace` 0.2.1. Если оба уже установлены и включены, переустанавливать их не нужно. Плагины сами читают токен из `.env\env.txt` целевого пользователя; отдельный файл запуска Codex и переменная в окружении Desktop не нужны. После изменения плагинов полностью перезапустите Codex обычным способом и откройте новую беседу для проверки инструментов.

Сценарий первого запуска создаёт выделенную стандартную сервисную учётную запись при её отсутствии и запрашивает пароль в повышенной консоли. Владельца существующего корня Tracker установщик не меняет. Для `tasks`, `state`, `logs` и `projects.json` используются их существующие данные; недостающие создаются на первом запуске. Корень `tasks` получает владельцем SID службы до первого создания задачи. `projects.json` доступен целевому пользователю только на чтение, а службе — на изменение. Инструкции размещаются в `tasks/AGENTS.md`; известные старые файлы в корне удаляются после успешной установки. Неизвестные файлы не удаляются и вызывают откат службы.

После успешной первой установки bootstrap JSON закрепляет SID созданной сервисной учётной записи для следующих запусков wrapper. Если установка не завершилась, это изменение JSON откатывается.

Проверки `tests/test-install-layout.ps1` моделируют прерванное переключение, откат первой установки, владельца `tasks` и сбой запуска службы при откате. Фактические SCM, ACL и MCP проверяются на рабочей машине во время интеграционного этапа.
