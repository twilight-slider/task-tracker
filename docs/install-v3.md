# Установка и переустановка TaskTracker v3

Установщик вызывается защищённым `Rebuild-TaskTracker.ps1` после административного bootstrap. Исходный код он берёт из чистой локальной ветки `main`, совпадающей с локальной `origin/main` и commit в `bootstrap.json`. Рабочая служба не выполняет файлы из клона.

Родительский каталог Tracker должен принадлежать Administrators/SYSTEM. По умолчанию запись, удаление и смена ACL для других учётных записей останавливают подготовку. Явный `-TrustAuthenticatedUsers` на обоих административных входах допускает права `Authenticated Users` и обычных Windows SID учётных записей; в таком режиме любой из этих пользователей с правом изменения родителя может повлиять на Tracker и файлы административного wrapper.

При первой установке административный bootstrap требует `-SnapshotRoots <абсолютный путь к корню проектов>`; допускается массив путей. При переустановке он сохраняет корни из установленного `service.json`, если параметр не указан. Пустой список запрещён. Перед остановкой службы скрипт проверяет целевого пользователя, путь Tracker, корни проектов, ACL, фактическую сервисную учётную запись и привязку Windows-службы. Он создаёт временные `bin` и `runtime` внутри `.protected`, из Python 3.11 в `PATH` создаёт venv, устанавливает `requirements.txt` через pip, проверяет импорт worker и компилирует C# host только при изменении `src/ServiceHost.cs`. Если исходник host не изменился, установленный EXE копируется побайтно.

Установщик до остановки службы клонирует опубликованную ветку `master` Git marketplace и требует в ней версии `task-folder-workflow` 0.6.0 и `task-tracker-mcp` 0.2.0 с прямыми HTTP MCP-конфигурациями. Локально изменённого репозитория недостаточно. После подготовки скрипт создаёт либо сверяет две копии MCP-токена, останавливает работающую службу, переключает установленные `bin`, `runtime` и `service.json`, запускает службу и проверяет состояние `Running/Automatic` и запрос MCP с токеном. При ошибке он возвращает прежние каталоги, конфигурацию, обе копии токена и ACL, удаляет вновь созданные службу и учётную запись и восстанавливает прежнее состояние службы. Если откат не завершился, старые файлы сохраняются в `.protected/.rollback-*`, а ошибка помечается `RECOVERY_INCOMPLETE`.

После запуска службы сценарий под TargetUser штатно подключает Git marketplace командой `codex plugin marketplace add`, если его нет, затем выполняет `codex plugin marketplace upgrade ai-marketplace` и при необходимости `codex plugin add` для обоих плагинов. Он проверяет версии и ответы обоих MCP scope. Если администратор вошёл под другой учётной записью, он вводит учётные данные TargetUser для запуска этого шага в его профиле. При сбое обновления плагинов новая служба остаётся запущенной, старая версия сохраняется в `.protected/.rollback-*`, выводится `PLUGIN_UPDATE_INCOMPLETE` для повторения обновления. Установщик копирует `Start-CodexWithTrackerToken.ps1` в папку `.env` целевого пользователя. Этот сценарий после закрытия действующего Codex Desktop читает токен из `env.txt` и запускает новый процесс `codex app` с переменной в памяти. Новый сеанс нужен для проверки инструментов плагинов; текущий процесс не перечитывает MCP-плагины на лету.

Сценарий первого запуска создаёт выделенную стандартную сервисную учётную запись при её отсутствии и запрашивает пароль в повышенной консоли. Владельца существующего корня Tracker установщик не меняет. Для `tasks`, `state`, `logs` и `projects.json` используются их существующие данные; недостающие создаются на первом запуске.

После успешной первой установки bootstrap JSON закрепляет SID созданной сервисной учётной записи для следующих запусков wrapper. Если установка не завершилась, это изменение JSON откатывается.

Проверки `tests/test-install-layout.ps1` моделируют прерванное переключение после первого каталога, сбой после полной замены и откат первой установки. Проверка фактического SCM, ACL и MCP выполняется на рабочей машине во время интеграционного этапа.
