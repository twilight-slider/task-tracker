# Установка и переустановка TaskTracker v3

Установщик вызывается защищённым `Rebuild-TaskTracker.ps1` после административного bootstrap. Исходный код он берёт из чистой локальной ветки `main`, совпадающей с локальной `origin/main` и commit в `bootstrap.json`. Рабочая служба не выполняет файлы из клона.

Родительский каталог Tracker должен принадлежать Administrators/SYSTEM. Обычным пользователям разрешён `Modify`, но не удаление дочерних объектов, изменение ACL или владельца. Корень Tracker не наследует права родителя; его допустимый владелец — Administrators, SYSTEM или фактическая сервисная учётная запись. Сервисная учётная запись получает полный доступ, целевой пользователь — только чтение и проход. Явный `-TrustAuthenticatedUsers` допускает более широкие права родителя при сознательном доверии их получателям.

При первой установке корневой `bootstrap.ps1` берёт корень снимков из `GIT_FOLDER` целевого пользователя; явный `-SnapshotRoots` задаёт один или несколько других абсолютных корней. Внутренний административный bootstrap получает выбранные корни параметром. При переустановке без параметра сохраняются корни из установленного `service.json`. Пустой список запрещён. Перед остановкой службы скрипт проверяет целевого пользователя, путь Tracker, корни проектов, ACL, фактическую сервисную учётную запись и привязку Windows-службы. Он создаёт временные `bin` и `runtime` внутри `.protected`, из Python 3.11 в `PATH` создаёт venv, устанавливает `requirements.txt` через pip, проверяет импорт worker и компилирует C# host только при изменении `src/ServiceHost.cs`. Если исходник host не изменился, установленный EXE копируется побайтно.

Установщик до остановки службы клонирует опубликованную ветку `master` Git marketplace и требует в ней версии `task-folder-workflow` 0.6.1 и `task-tracker-mcp` 0.2.1 с MCP-клиентом внутри плагина, который читает токен из пользовательского `env.txt` и обращается к HTTP endpoint службы. Локально изменённого репозитория недостаточно. После подготовки скрипт создаёт либо сверяет две копии MCP-токена, останавливает работающую службу, переключает установленные `bin`, `runtime` и `service.json`, запускает службу и проверяет состояние `Running/Automatic` и запрос MCP с токеном. При ошибке он возвращает прежние каталоги, конфигурацию, обе копии токена и ACL, удаляет вновь созданные службу и учётную запись и восстанавливает прежнее состояние службы. Если откат не завершился, старые файлы сохраняются в `.protected/.rollback-*`, а ошибка помечается `RECOVERY_INCOMPLETE`.

После запуска службы сценарий под TargetUser штатно подключает Git marketplace командой `codex plugin marketplace add`, если его нет, затем выполняет `codex plugin marketplace upgrade ai-marketplace` и при необходимости `codex plugin add` для обоих плагинов. Он проверяет версии и ответы обоих MCP scope. Если администратор вошёл под другой учётной записью, он вводит учётные данные TargetUser для запуска этого шага в его профиле. При сбое обновления плагинов новая служба остаётся запущенной, старая версия сохраняется в `.protected/.rollback-*`, выводится `PLUGIN_UPDATE_INCOMPLETE` для повторения обновления. Плагины сами читают токен из `.env\env.txt` целевого пользователя; отдельный файл запуска Codex и переменная в окружении Desktop не нужны. После обновления плагинов полностью перезапустите Codex обычным способом и откройте новую беседу для проверки инструментов; текущий процесс не перечитывает MCP-плагины на лету.

Сценарий первого запуска создаёт выделенную стандартную сервисную учётную запись при её отсутствии и запрашивает пароль в повышенной консоли. Владельца существующего корня Tracker установщик не меняет. Для `tasks`, `state`, `logs` и `projects.json` используются их существующие данные; недостающие создаются на первом запуске. `projects.json` доступен целевому пользователю только на чтение, а службе — на изменение. Инструкции размещаются в `tasks/AGENTS.md`; известные старые файлы в корне удаляются после успешной установки. Неизвестные файлы не удаляются и вызывают `ROOT_CLEANUP_INCOMPLETE`.

После успешной первой установки bootstrap JSON закрепляет SID созданной сервисной учётной записи для следующих запусков wrapper. Если установка не завершилась, это изменение JSON откатывается.

Проверки `tests/test-install-layout.ps1` моделируют прерванное переключение после первого каталога, сбой после полной замены и откат первой установки. Проверка фактического SCM, ACL и MCP выполняется на рабочей машине во время интеграционного этапа.
