# `/mcp/jobs` в Windows-службе: исходный контракт

Windows `ServiceHost` принимает `start`, `status`, `reply`, `stop` на `/mcp/jobs` с тем же Bearer-токеном, проверкой `Host` и ограничением размера, что у `/mcp/folders`. Отдельный экземпляр Python worker пересылает вызов на `127.0.0.1:38774/mcp/jobs`; основной worker одновременно обслуживает папки и снимки. Это необходимо, потому что WSL-исполнитель при запуске задания сверяет ключ задачи через `/mcp/folders`. Ответ и ошибки возвращаются вызывающему клиенту как MCP `structuredContent`. Токен читается из защищённого `<Tracker>/.protected/mcp-token` и не выводится в журнал.

Порт 38774 предназначен для Python-исполнителя в WSL, который запускает Codex в контейнерах. `linux_mcp.py` получает `windowsServiceUrl` и `externalTasksRoot` в своём `service.json`: папки и снимки он читает через Windows-службу, а фиксированный `agentTaskUpdate` выбирает из `/mnt/d/.../tasks`. Очередь, защищённый индекс и сессии Codex находятся в отдельных закрытых каталогах ext4. WSL-исполнитель хранит закрытую копию токена Windows-службы; значения обеих копий при развёртывании должны совпадать. Вызов `status` из Windows-службы запрашивает краткий ответ без большого журнала событий. Это позволяет проверить AIDEV-79 без переноса исходных папок. Текущая схема выдаёт `agentTaskUpdate` одной задаче; для других задач понадобится отдельная проверка динамического назначения каталога. До запуска и проверки этого WSL-исполнителя маршрут вернёт `JOB_BACKEND_UNAVAILABLE`; рабочее исполнение не заявляется.

Контейнер Django обращается к Windows-службе через её дополнительную привязку `mcpWslAddress` к адресу интерфейса WSL. Адрес выбирает администратор параметром `-McpWslAddress` при bootstrap; привязка не открывает службу на всех интерфейсах. Брандмауэр Windows должен разрешить вход с WSL к этому точному адресу и порту. Без `mcpWslAddress` служба по-прежнему слушает только Windows `127.0.0.1`. Если адрес WSL изменится, loopback останется доступен, но адрес для контейнеров нужно обновить и перезапустить службу.

Проверки исходного контракта: `tests/test-servicehost-mcp.ps1` проверяет авторизацию и область `/mcp/jobs`; `tests/test_python_worker.py` проверяет перенос Bearer-токена и результата к тестовому backend; `tests/test_windows_service_proxy.py` проверяет обратный вызов WSL → Windows и привязку задачи к выбранному `update`. Действующая служба не обновлена. Развёртывание выполняется позже по `AGENTS.md` через bootstrap из чистой `main` после проверки исходников, WSL-исполнителя и сетевых правил.
