# Административный первый запуск TaskTracker

Новый путь установки использует корневой раппер, запускаемый в повышенной PowerShell с именем целевого пользователя:

```powershell
pwsh -NoProfile -File ./bootstrap.ps1 -TargetUser 'DOMAIN\User'
```

На родительском каталоге допускается `Modify` для обычных пользователей, если это не даёт удаления дочерних объектов, смены ACL или владельца. Если есть такие дополнительные права и администратор сознательно доверяет их получателям, раппер запускается с `-TrustAuthenticatedUsers`. Флаг сохраняется в `bootstrap.json` и повторно учитывается wrapper и установщиком.

Раппер сначала проверяет чистую `main` и совпадение `HEAD` с локальной `origin/main`. При первом запуске без `-SnapshotRoots` он читает `GIT_FOLDER` из `<профиль TargetUser>\.env\env.txt` и проверяет, что каталог существует и задан абсолютным путём, до изменения файлов. Затем внутренний `Prepare-TrackerRoot.ps1` читает `TRACKER_FOLDER` из того же файла, проверяет выделенный родительский каталог и создаёт отсутствующие корень Tracker и `.protected`. Владельца существующего Tracker он не меняет. Если `.env` отсутствует, путь относительный, владелец или ACL небезопасны, он останавливается с указанием причины. Не размещайте Tracker внутри профиля пользователя или общей системной папки.

Сервисная учётная запись входит в доверенный перечень владельцев корня Tracker вместе с Administrators и SYSTEM и получает полный доступ. Её SID сверяется с фактической учётной записью установленной Windows-службы. Корень Tracker не наследует ACL родителя и не допускает запись иных пользователей; владелец родителя — Administrators или SYSTEM.

Внутренний `Bootstrap-TaskTrackerAdmin.ps1` повторно проверяет, что репозиторий task-tracker находится на `main`, текущий HEAD совпадает с локальной `origin/main`, а индекс и рабочее дерево чисты, включая untracked файлы. Сетевой `fetch` не выполняется. При первой установке он требует `-SnapshotRoots` с одним или несколькими абсолютными корнями проектов; при повторной может сохранить уже установленные корни. Затем он повторно читает `.env` TargetUser, проверяет защищённую область и создаёт в ней `bootstrap.json`, административный wrapper и его общий код. Bootstrap не меняет владельца Tracker. JSON закрепляет commit и источник опубликованного ai-marketplace.

Корневой bootstrap сам запускает `<Tracker>\.protected\TaskTracker-AdminWrapper.ps1`. Wrapper повторяет проверки Git, профиля, путей и ACL, после чего создаёт защищённый `Rebuild-TaskTracker.ps1` и продолжает установку. Для отдельной проверки wrapper без установки доступен `-PrepareOnly`. Изменения в репозитории после bootstrap требуют повторного запуска корневого bootstrap из чистой `main`.

MCP токен хранится только в `<Tracker>\.protected\mcp-token` и `TRACKER_MCP_TOKEN` в `.env\env.txt` TargetUser. `Sync-TaskTrackerToken.ps1` создаёт обе копии при первой установке, сохраняет и сверяет их при повторной, а `-Rotate` заменяет обе копии по отдельной административной команде. Значение токена не выводится. Проверка работающей службы и откат ротации включаются в сценарий установки.

При отдельной ротации служба должна быть запущена: скрипт перезапускает её и проверяет запрос к MCP с новым токеном. Если проверка не проходит, он восстанавливает обе прежние копии, снова запускает службу и проверяет старый токен. Файлы `.env\env.txt` и JSON читаются как UTF-8, в том числе в Windows PowerShell 5.1.

Wrapper использует установщик v3 и проверяет опубликованные MCP-конфигурации marketplace до замены службы. Установщик размещает инструкции в `tasks/AGENTS.md`, удаляет известные старые файлы из корня Tracker и оставляет там только `projects.json` помимо каталогов `tasks` и `.protected`. Плагины сами читают `TRACKER_MCP_TOKEN` из `<профиль TargetUser>\.env\env.txt` при подключении к службе. После установки полностью перезапустите Codex обычным способом.
