# Административный первый запуск TaskTracker

Новый путь установки использует два скрипта репозитория, оба запускаются в повышенной PowerShell с именем целевого пользователя:

```powershell
pwsh -NoProfile -File scripts/Prepare-TrackerRoot.ps1 -TargetUser 'DOMAIN\User'
pwsh -NoProfile -File scripts/Bootstrap-TaskTrackerAdmin.ps1 -TargetUser 'DOMAIN\User' -SnapshotRoots @('<полный путь к корню проектов>')
```

Если администратор сознательно доверяет всем `Authenticated Users` с правами записи на родительский каталог Tracker, оба входа запускаются с `-TrustAuthenticatedUsers`. Флаг сохраняется в `bootstrap.json` и повторно учитывается wrapper и установщиком. Без него широкий доступ родителя останавливает подготовку.

Первый скрипт читает `TRACKER_FOLDER` из `<профиль TargetUser>\.env\env.txt`, проверяет выделенный родительский каталог и создаёт отсутствующие корень Tracker и `.protected`. Владельца существующего Tracker он не меняет. Если `.env` отсутствует, путь относительный, владелец или ACL небезопасны, он останавливается с указанием причины. Не размещайте Tracker внутри профиля пользователя или общей системной папки.

Сервисная учётная запись считается доверенной для административных файлов в Tracker. У существующей установки владелец корня может быть этой учётной записью: её SID сверяется с фактической учётной записью установленной Windows-службы. Владельцы и права записи иных пользователей у корня и его родительского каталога отклоняются.

Второй скрипт до записи файлов проверяет, что репозиторий task-tracker находится на `main`, текущий HEAD совпадает с локальной `origin/main`, а индекс и рабочее дерево чисты, включая untracked файлы. Сетевой `fetch` не выполняется. При первой установке он требует `-SnapshotRoots` с одним или несколькими абсолютными корнями проектов; при повторной может сохранить уже установленные корни. Затем он повторно читает `.env` TargetUser, проверяет защищённую область и создаёт в ней `bootstrap.json`, административный wrapper и его общий код. Bootstrap не меняет владельца Tracker. JSON закрепляет commit и источник опубликованного ai-marketplace.

Далее администратор запускает `<Tracker>\.protected\TaskTracker-AdminWrapper.ps1`. Wrapper повторяет проверки Git, профиля, путей и ACL, после чего создаёт защищённый `Rebuild-TaskTracker.ps1`. Для проверки без установки доступен `-PrepareOnly`. Обычный запуск продолжает установку через защищённый rebuild script. Изменения в репозитории после bootstrap требуют повторного административного bootstrap из чистой `main`.

MCP токен хранится только в `<Tracker>\.protected\mcp-token` и `TRACKER_MCP_TOKEN` в `.env\env.txt` TargetUser. `Sync-TaskTrackerToken.ps1` создаёт обе копии при первой установке, сохраняет и сверяет их при повторной, а `-Rotate` заменяет обе копии по отдельной административной команде. Значение токена не выводится. Проверка работающей службы и откат ротации включаются в сценарий установки.

При отдельной ротации служба должна быть запущена: скрипт перезапускает её и проверяет запрос к MCP с новым токеном. Если проверка не проходит, он восстанавливает обе прежние копии, снова запускает службу и проверяет старый токен. Файлы `.env\env.txt` и JSON читаются как UTF-8, в том числе в Windows PowerShell 5.1.

Старые `Bootstrap-TaskTracker.ps1` и `Install-TaskTracker.ps1` относятся к действующей Node.js установке на переходный период. Новый wrapper использует установщик v3 и проверяет опубликованные MCP-конфигурации marketplace до замены службы. После установки запускайте Codex через `<профиль TargetUser>\.env\Start-CodexWithTrackerToken.ps1`, предварительно закрыв прежний процесс Desktop.
