# Tracker в Ubuntu/WSL 2: контейнерный путь

Образ `Dockerfile.tracker` запускает операции папок и снимков через MCP HTTP. Защищённый индекс заданий и маршрут `/mcp/jobs` предоставляют `start`, `status`, `reply`, `stop`, `update_repositories`. Образ использует Python 3.11 и Git, запускается как UID/GID 1000:1000. При заданных `agentImage` и `agentSessionRoot` Tracker запускает Codex CLI в отдельном контейнере Docker. Рабочая установка относится к T8.

## Хранение и доступ

Контейнер получает конфигурацию `service.json` с `schemaVersion: 2`, `securityMode: "linux-container"` и абсолютными путями внутри контейнера: `trackerRoot`, `tasksRoot` (`<trackerRoot>/tasks`), `protectedRoot`, `snapshotRoots`. `FolderStore` сохраняет существующий JSON-контракт worker и закрывает служебные каталоги режимом 0700. На drvfs права `chmod` могут отличаться от ext4; граница для агента задаётся списком bind mount: агенту выдаются только назначенный `update` и репозитории. `.protected`, `ai_actions`, конфигурация, MCP-токен и Docker socket агенту не подключаются.

Tracker читает токен из отдельного файла через `--token-file`. MCP HTTP имеет маршруты `/mcp/folders` и `/mcp/snapshots`, требует Bearer-токен и проверяет область инструмента. Порт следует публиковать только на `127.0.0.1` хоста WSL. Токен и защищённое состояние хранятся в каталоге, доступном только Tracker; тестовый токен из `.runtime/tests` не подходит для рабочей установки.

HTTP ограничивает число одновременных соединений до 16 и отводит 30 секунд на чтение запроса. После полного чтения операция worker завершается без принудительного обрыва по этому сроку, включая ожидание очереди.

`start` быстро сохраняет `job_id` и отдельный `control_key` для управления этим заданием. Ключ выдаётся только при создании, в индексе хранится его SHA-256. Запросы `status/reply/stop/update_repositories` с чужим ключом получают `JOB_NOT_FOUND`; второй активный turn для того же `thread_id` получает `THREAD_BUSY`. Каждый запуск получает постоянный `run_id`; контейнер именуется по родителю и попытке, а метки сверяются перед запуском, наблюдением и остановкой. Потерянный ответ Docker Engine не вызывает повторного создания или запуска: исход остаётся `unknown`, если inspect не может его подтвердить. После перезапуска Tracker сверяет сохранённые попытки с Docker; выполняющийся контейнер наблюдается до завершения, завершившийся восстанавливает результат из logs. Отсутствующий или неопределённый контейнер остаётся `unknown`.

`Dockerfile.agent` собирает общий образ с Codex CLI 0.149.0. Tracker передаёт prompt в `codex exec --json`; при `reply` использует сохранённый родной `codex_thread_id` и `codex exec resume --json`. Каждый turn запускается в новом контейнере с тем же собственным каталогом `/home/agent/.codex`. Завершённый turn становится `waiting`: `status` возвращает ответ, родной ID и JSONL events. Если терминальное событие, ID или ответ отсутствуют, исход остаётся `unknown`, и Tracker не запускает turn повторно. `stop` останавливает контейнер и возвращает `stopped` только после inspect, когда процесс в контейнере уже не работает.

Агенту не подключается Docker socket или закрытое состояние Tracker. `agentTaskUpdate` задаёт только каталог `update`; `agentRepositories` задаёт доверенный каталог ID → абсолютный канонический путь, а `agentInitialRepositories` — исходные ID. Старый `agentRepository` остаётся одним каталогом с ID `assigned`. Пути должны быть обычными абсолютными каталогами и не пересекаться друг с другом, с `agentTaskUpdate` и `agentSessionRoot`. `agentSessionRoot` должен быть каталогом ext4 владельца Tracker с правами 0700; отдельная сессия родителя также получает 0700. Сеть агенту нужна для Codex. Общий образ содержит ограниченный bundle Ponytail 5.3.2 из локального установленного cache: skill, plugin manifest и hook scripts в `/opt/agent-bundle`; в отдельном `CODEX_HOME` создаются только ссылки. Учётные данные, историю сессий и конфигурацию пользователя образ не включает. Полный утверждённый состав расширений и проверка активации hooks остаются для T8. Если `agentImage` и `agentSessionRoot` не заданы, `start` по-прежнему только резервирует задание. `update_repositories` возвращает `REPOSITORY_UPDATE_NOT_READY`.

`update_repositories` требует `job_id`, `control_key`, массив ID `repositories` из доверенного каталога и `expected_rights_version`. Права, версия и незавершённое изменение сохраняются для родителя в защищённом SQLite. При совпадении версии Tracker сначала сохраняет `pending`, блокирует новые `start` и `reply`, затем останавливает все контейнеры этого родителя и проверяет для каждого `Running=false` и `Pid=0`. Только после этого он сохраняет новые права, увеличивает версию и снимает барьер. Неопределённый ответ Docker оставляет `pending`; после рестарта можно повторить тот же запрос с исходной версией, без запуска нового turn. Параллельный запрос со старой версией получает конфликт; чужой ключ не раскрывает состояние. Уже запущенный turn, прерванный отзывом, может завершиться `unknown`; Tracker не принимает его старый результат под новой версией прав.

Граница mount предотвращает доступ к отозванному каталогу по его пути. На выбранном drvfs символьная ссылка из разрешённого репозитория на отозванный путь не сработала, но заранее созданная жёсткая ссылка позволила изменить тот же inode. Поэтому перед выдачей права записи Tracker рекурсивно проверяет разрешённые репозитории и `agentTaskUpdate`, включая скрытые файлы, и отвергает любой обычный файл с числом жёстких ссылок больше одного; ошибка обхода каталога также закрывает доступ. При таком отказе `update_repositories` сохраняет `pending` после остановки. Внешний процесс хоста всё ещё может создать ссылку после проверки; для рабочей установки T8 требуется исключить такое одновременное изменение или физически разделить хранилища.

Для проверки из корня репозитория собираются `Dockerfile.tracker` и `Dockerfile.agent`. Контрактные тесты `test_linux_tracker.py`, `test_python_worker.py`, `test_job_queue.py` и `test_docker_controller.py` запускаются в Ubuntu/WSL 2 внутри Python 3.11 Bookworm. Реальный тест Docker включается через `TRACKER_DOCKER_TEST=1`, Codex turn/resume — через `TRACKER_CODEX_TEST=1`; оба используют `TRACKER_TEST_SESSION_ROOT` (ext4). Тестовый Tracker получает Docker socket, выбранный `update` и репозиторий передаются через `TRACKER_TEST_UPDATE` и `TRACKER_TEST_REPO`. Агентский контейнер получает только выбранные mount. Тестовая авторизация должна находиться только в отдельных закрытых каталогах Ubuntu и удаляться после проверки. Тестовые файлы находятся в `.runtime/tests` и игнорируются Git.

## T8: изолированная установка и откат

`scripts/wsl_install.py` запускается **в Ubuntu/WSL 2** от пользователя UID/GID 1000. Он проверяет закрытые каталоги ext4, токен длиной от 32 символов с режимом 0600, схему `service.json`, разделение защищённых путей и существование каталогов для чтения. Docker socket монтируется только Tracker; конфигурация и каталоги снимков подключаются к нему без права записи. Агент получает только свой каталог сессии, выбранный `update` и назначенные репозитории. Публикуемый порт принимает только `127.0.0.1`; внутри контейнера используется тот же номер, потому что HTTP проверяет заголовок Host.

Подготовьте три **раздельных** каталога ext4 с режимом 0700: `config`, `data`, `sessions`, а также отдельный `state` для записей установки. В `config/service.json` задайте абсолютные пути Ubuntu. Пример схемы (замените все пути на проверенные конечные):

```json
{
  "schemaVersion": 2,
  "securityMode": "linux-container",
  "trackerRoot": "/home/user/tracker/data",
  "tasksRoot": "/home/user/tracker/data/tasks",
  "protectedRoot": "/home/user/tracker/data/.protected",
  "snapshotRoots": ["/mnt/d/Projects/Git/ai-reps/task-tracker"],
  "agentImage": "task-tracker-agent:user-plugins-t8",
  "agentSessionRoot": "/home/user/tracker/sessions",
  "agentTaskUpdate": "/home/user/tracker/data/tasks/2026/STAGE-1/update",
  "agentRepositories": {"task-tracker": "/mnt/d/Projects/Git/ai-reps/task-tracker"},
  "agentInitialRepositories": ["task-tracker"]
}
```

Пример выше намеренно использует синтетическую `STAGE-1`: каталог `update` уже должен существовать внутри указанного `tasksRoot`. Для фактической AIDEV-79 папка находится на `/mnt/d/Projects/Tracker/tasks/2026/AIDEV-79`, а текущий установщик требует `tasksRoot=<trackerRoot>/tasks` при приватном ext4 `trackerRoot`. Подставить drvfs `tasksRoot` отдельно сейчас нельзя: проверка схемы отклонит такую конфигурацию. Рабочий T8.8 switch требует отдельно проверенного решения по конечным путям; копирование или перенос задачи здесь не выполнялись.

Создайте случайный токен в `config/mcp-token`, закройте файл режимом 0600; его значение не следует помещать в конфигурацию, командную строку или логи. Проверьте оба Docker-образа, затем выполните `python3 scripts/wsl_install.py check /home/user/tracker/config`. После проверки:

```sh
docker build -f Dockerfile.tracker -t task-tracker:t8-candidate .
python3 scripts/export_agent_bundle.py --codex-home /mnt/c/Users/Vasil/.codex
docker build -f .runtime/agent-export/context/Dockerfile.agent \
  -t task-tracker-agent:user-plugins-t8 .runtime/agent-export/context
python3 scripts/wsl_install.py install /home/user/tracker/config \
  --state /home/user/tracker/state --name task-tracker --port 38772 \
  --image task-tracker:t8-candidate
```

Повторная установка с тем же именем работает только при неизменной конфигурации старого экземпляра. Она проверяет его приватные mount и порт, делает консистентную копию `.protected/jobs.sqlite` в `state/<время>/jobs.sqlite`, сохраняет исходный `service.json`, ID старого образа и прежнее состояние running/stopped **до** остановки. При ошибке запуска установщик пытается автоматически вернуть старый контейнер; запись остаётся для ручного отката, если восстановление также не удалось. `rollback` принимает напечатанный каталог записи установки: `python3 scripts/wsl_install.py rollback /home/user/tracker/state/<время>`. Откат восстанавливает исходный `service.json` (позднейшую версию сохраняет в записи), прежний образ и running/stopped, но **не** затирает текущую SQLite базу более старой копией; данные и backup остаются для ручного восстановления. Если установка была первой, откат удаляет только контейнер. При аварии после удаления старого контейнера запись установки позволяет повторить `rollback`.

Автоматический тест `PYTHONDONTWRITEBYTECODE=1 python3 tests/wsl_stage_smoke.py` создаёт пустой временный ext4 root, проверяет folder/snapshot API, токен, loopback, mount, перезапуск, резервную копию SQLite и путь rollback, затем убирает временный контейнер и root. В smoke повторно устанавливается тот же образ: фактическую смену версии образа тест не доказывает. Тест не запускает Codex и не использует рабочие каталоги. Метрики сохраняются в `.runtime/tests/t8-stage/result.json`.

T8.8 pre-install dry run 2026-10-21 на текущих образах прошёл: первый запуск 2.263 с, restart 11.486 с, повторная установка 13.013 с; folder/snapshot, SQLite backup и rollback прошли. Изолированный Tracker и каталоги удалены. Рабочее переключение остаётся закрытым из-за T8.7 live rate limit и выбора конечного хранилища для всех 59 существующих папок. [План миграции](t8-storage-migration-plan.md) включает исходный hash inventory, пробу на синтетических ext4/drvfs данных и конфликтно-безопасный обратный ход; реальные задачи не копировались.

Ограничение повторной установки на неизменную конфигурацию выше относится к запуску без `--previous-config`. Проверенный путь изменения описан далее.

### T8: ограниченный доступ агента к MCP для назначенной задачи

В `jobs/start` теперь можно передать `task_key` — существующий ключ задачи, проверяемый через `resolve_task_folder`. Первый такой вызов навсегда связывает родительский `thread_id` с этим ключом; другой ключ для того же родителя отклоняется. Старые вызовы без `task_key` продолжают работу без выдачи агенту MCP-доступа. Для связанного родителя Tracker перед каждым turn создаёт случайный токен, сохраняет в защищённой SQLite только SHA-256 и срок действия (24 часа), а само значение кладёт в закрытый `plugin-env.json` только его сессии. `TRACKER_MCP_BASE_URL`, `TRACKER_MCP_TOKEN` и `TRACKER_TASK_KEY` не входят в образ, Docker Env или логи; глобальный `mcp-token` агенту не выдаётся. Завершение или остановка turn, а также начало изменения прав отзывают токен. После перезапуска Tracker хеш сохраняется для ещё работающего контейнера и сверяется с его состоянием при восстановлении.

Ограниченный токен разрешает для назначенного ключа `resolve_task_folder`, `set_task_jira_host` только у уже существующей Jira-задачи, `create_task_subdirectory` и три snapshot-инструмента. Создание снимка принимает только путь вида `/workspace/repos/<назначенный-id>/...`; Tracker переводит его в собственный доверенный путь репозитория и отклоняет сырой host-путь, `..`, ссылки и отозванный репозиторий. Чтение и сравнение ранее созданного снимка также проверяют текущие права на его репозиторий. Другой ключ возвращает `TASK_NOT_FOUND`; глобальный список проектов, создание новых задач и `/mcp/jobs` закрыты. Проверка права, вызов worker и отзыв сериализованы одним замком.

Пять остальных folder-инструментов (`get_tasks_folder`, `get_task_projects`, `register_task_project`, `create_task_folder`, `create_local_task_folder`) доступны через отдельный привилегированный host-вызов `/mcp/jobs` → `bootstrap_folder`. Host передаёт `thread_id`, точную операцию и точные аргументы, используя глобальный MCP-токен **только у Tracker/host**. Требуется активная привязка родителя к задаче. Tracker записывает SHA-256 одноразового допуска в защищённую SQLite, ограничивает его срок 5 минутами и текущим сроком родительского токена и запускает короткий отдельный agent image container. В нём работает установленный task-folder-workflow MCP; контейнер получает только собственную временную сессию и сеть, без task/repo bind и Docker socket. Секрет передаётся через файл `plugin-env.json` 0600, отсутствует в Docker Env, команде и логах. Допуск расходуется до исполнения, повторный вызов запрещён; stop/изменение прав отзывают неиспользованные допуски. После создания локальной задачи host получает новый `key` и запускает **нового** родителя с явным `task_key` для этой задачи. Tracker завершает и удаляет bootstrap-контейнер и временную сессию при подтверждённом исходе; при неопределённом ответе Docker не повторяет операцию и отзывает допуск.

Изолированные проверки: `tests/test_scoped_writes.py` внутри Python 3.11 Docker проверяет разрешённые и запрещённые вызовы всех 8 folder и 3 snapshot-инструментов, включая чужой ключ, `..`, ссылку, отозванный репозиторий, одноразовость и остановку во время записи. `tests/wsl_scope_network_smoke.py` проверяет доступ из отдельного agent-контейнера к назначенной задаче и снимкам. `tests/wsl_exact_grant_smoke.py` проверяет пять операций через установленный plugin в отдельном контейнере и privileged `bootstrap_folder`, возврат нового key, отклонение дубля и отзыв неиспользованного допуска. Результаты лежат в `.runtime/tests/t8-scope-network/` и `.runtime/tests/t8-exact-grants/`.

Для связи контейнеров создайте отдельную пользовательскую Docker bridge сеть и укажите её имя в `agentNetwork` конфигурации. Установщик проверяет существование локальной bridge сети, подключает Tracker под именем `tracker-mcp` и оставляет публикацию хостового порта на `127.0.0.1`; агент подключается к этой сети без Docker socket. Плагины с зашитым `127.0.0.1` ещё требуют отдельной адаптации их локальной копии в образе: наличие сетевого адреса и токена само по себе не меняет их поведение.

Если задан фиксированный `agentTaskUpdate`, `jobs/start` требует явный `task_key`: каталог из `resolve_task_folder` должен совпадать с родителем именно этого `update`. Другой существующий ключ и вызов без ключа отклоняются до запуска агента. Это ограничивает текущую схему одной задачей на фиксированный mount; для нескольких задач нужен отдельный выбор mount по родителю. Когда `update` лежит внутри `trackerRoot/tasks`, установщик использует уже подключённый каталог данных Tracker и не добавляет второй bind поверх него.

Для изменения `service.json` уже установленного Tracker заранее сохраните **точный старый файл** в закрытом ext4 каталоге (0700) с режимом файла 0600. После изменения конфигурации укажите `--previous-config <путь-к-старому-файлу>` при `wsl_install.py install`. Установщик сверяет SHA-256 старого файла с меткой работающего контейнера, не допускает переноса приватных каталогов, делает backup SQLite и записывает старый файл для отката до остановки контейнера. `rollback` восстанавливает старую конфигурацию, образ и прежнее running/stopped состояние. Изолированный тест `.runtime/tests/t8-scope-network/result.json` прошёл путь установки без сети → обновления с сетью → ограниченного доступа → отзыва → отката обеих установок.

Обновление по экспортированному образу: `python3 scripts/export_agent_bundle.py --codex-home /mnt/c/Users/Vasil/.codex` запускается в Ubuntu/WSL 2 и создаёт контекст `.runtime/agent-export/context`. Для сборки используйте `docker build -f .runtime/agent-export/context/Dockerfile.agent -t task-tracker-agent:user-plugins-t8 .runtime/agent-export/context`. В него входят только 10 включённых пользовательских marketplace plugins и 8 standalone skills; нативные плагины OpenAI исключены. Экспорт копирует только разрешённые файлы, отвергает символьные ссылки и сохраняет SHA-256 каждого файла в `.runtime/tests/agent-export/manifest.json`. Версии пакетов зафиксированы именами каталогов, но байты исходного cache пока не сверяются с заранее зафиксированным эталонным хешем. Автономный `tests/wsl_agent_bundle_smoke.py` подтвердил обнаружение всех 10 plugins, 8 skills, 4 MCP definitions, запуск `codex plugin add` при первом и повторном создании контейнера, передачу синтетической переменной и прямой эффект скрипта Ponytail. Это не доказывает работу MCP с реальными сервисами или событие SessionStart в Codex.

`agentEnvironment` в `service.json` задаёт явное соответствие имени переменной и имени файла в закрытом `config/secrets` (0700). Каждый файл требует режим 0600. Tracker читает значения непосредственно перед запуском агента и атомарно записывает их в `plugin-env.json` отдельной сессии родителя (0600); образ, Docker Env, команда и логи значений не содержат. При повторном запуске значения обновляются, при удалении mapping файл удаляется. Это предоставляет переменные только конкретному агенту, которому принадлежит сессия; агент имеет доступ к своим выданным значениям. Рабочие секреты, в том числе глобальный MCP-токен Tracker, в этот allowlist не включайте. После смены прав или ротации секрета остановите старый контейнер родителя и запустите новый turn, чтобы новый процесс получил актуальные значения.

Для Jira 0.4.0 назначьте только нужному родителю `JIRA_BASE_URL`, `JIRA_API_TOKEN` и при необходимости `JIRA_API_PATH`, `JIRA_TYPE`, `JIRA_AUTH_TYPE`, `JIRA_EMAIL` через отдельные файлы `config/secrets` и этот allowlist. Многопрофильный `JIRA_ENV_DIR` поддерживается самим plugin, но автоматическое копирование каталога профилей из host в сессию Tracker пока не реализовано; рабочая конфигурация использует один явно выданный профиль. Изолированный контейнерный MCP smoke подтвердил оба инструмента Jira с подставными HTTPS-ответами (2 положительных и 3 отказных сценария), а один ограниченный read существующей Jira вернул `found`. Значения токенов не записывались в образ, Docker Env/Cmd, логи или результаты; одноразовые ext4 сессии удалены. Несекретные результаты: `.runtime/tests/t8-jira/result.json` и `live-result.json`.

При экспорте `scripts/patch_agent_plugins.py` адаптирует **только копии** пользовательских Node MCP файлов: task-folder-workflow, task-tracker-mcp и snapshot client Train Driver. Каждый исходный файл проверяется по точному SHA-256; при обновлении установленного plugin экспорт останавливается до пересмотра адаптера. В Linux эти копии требуют `TRACKER_MCP_BASE_URL=http://tracker-mcp:<порт>` и ограниченный `TRACKER_MCP_TOKEN`, а без них завершаются с ошибкой до чтения старого `~/.env/env.txt`. На Windows исходные установленные файлы не меняются. T8.4 подтвердил task-folder-workflow и task-tracker-mcp для собственной задачи и назначенного репозитория, а пять bootstrap folder-операций — в отдельных краткоживущих контейнерах. Обычный task-scoped агент не получает глобальный `/mcp/jobs`; новые проекты и задачи запускает доверенный host через точный одноразовый допуск. Полная интеграция с реальными внешними сервисами остаётся отдельной проверкой.

Agent Dockerfile устанавливает `python3`, `py3-pip`, `git` и `ripgrep`. Экспорт адаптирует только проверенные по SHA-256 копии standalone skills: Linux пути для Python validator и локального Git/search, явное ограничение Excel COM и отказ `apply_s2t_blocks.py` **до записи XLSX**, если на Linux не задан `--skip-excel-validation`. В установленном образе T8.6 обнаружены все 8 standalone skills с ресурсами. Шесть локальных Python/shell сценариев прошли на малых YAML/XLSX fixture: сортировка и дубли CDC, OOXML audit и CSV export, S2T запись только с явным fallback, Linux runtime check, а также новый Python-порт `download_s2t_attachment.py` с подставными HTTPS metadata/download и отказом от ссылки на чужой origin. Исходный Windows `.ps1` и cache не изменены. Результат — `.runtime/tests/t8-standalone8/result.json`. Реальный Confluence не проверен: стандартный профиль `~/.env/confluence.env` отсутствует в этом окружении. Для запуска Python-порта нужны per-agent `CONFLUENCE_BASE_URL` и `CONFLUENCE_API_TOKEN` через защищённый `agentEnvironment`; redirect на другой origin запрещён.

Decision gate для остальных Windows helpers: SQL Server helper требует `sqlcmd.exe` и Windows Integrated Auth (`-E`); Linux `sqlcmd`/Kerberos профиль в образе отсутствуют. Kafka helper требует `kafka-run-class.bat`; Linux Kafka CLI, JAAS/сертификаты и broker-профиль не предоставлены. HelpDesk helper использует `C:\Tools\helpdesk-local\helpdesk-local.ps1` как auth/HTTP transport; Linux transport/учётные данные отсутствуют. Excel COM для проверки живого `.Value2`/`.Text` недоступен в Linux; OOXML fallback не доказывает пересчёт Excel. `linux-runtime-check.sh` возвращает отказ для этих режимов и не заменяет подключения к сервисам.
